# DEVARA STAGE 2 — EXHAUSTIVE INDEPENDENT FORENSIC AUDIT

## MISSION

Perform the most exhaustive independent audit reasonably possible of **Stage 2: Syntax Analysis / Parsing** of the Devara compiler.

This is a VERIFICATION TASK, NOT an implementation task.

Your objective is to answer one question:

> Does the current Stage 2 implementation actually satisfy the canonical Devara language specification and the frozen Stage 2 design, with sufficient evidence to justify declaring Stage 2 complete?

Do not make the implementation look correct.

Try to BREAK it.

Try to find:
- grammar violations
- missing grammar alternatives
- incorrectly accepted syntax
- incorrectly rejected syntax
- precedence/associativity bugs
- AST construction bugs
- AST contract violations
- source-span bugs
- token-consumption bugs
- parser state bugs
- ambiguity bugs
- error-recovery bugs
- diagnostic bugs
- infinite-loop/non-progress bugs
- malformed-input crashes
- missing test coverage
- weak tests that would allow broken parser behavior to pass
- accidental language extensions
- accidental restrictions
- contradictions between specification, design, implementation, and tests
- assumptions that were never actually specified
- parser behavior that would create problems for later compiler stages

The final result must be an evidence-backed audit, not a confidence statement.

YOU ARE AN AUDITOR.

You must NOT modify:

- source code
- parser implementation
- AST implementation
- lexer implementation
- tests
- language specification
- Stage 2 design document
- configuration
- project metadata
- generated tracked files

Do not "fix" anything you find.

Do not rewrite anything.

Do not silently patch anything to see whether tests pass.

Do not commit anything.

Do not alter the repository state.

If experimentation is necessary, use:
- read-only analysis
- subprocesses
- temporary copies
- temporary files outside the repository
- in-memory transformations

Any experimental mutation must be isolated and must not modify tracked project files.

At the beginning and end, verify repository cleanliness if the environment permits it.

If you accidentally modify anything, immediately revert it and disclose that incident.

# 48. SEVERITY RULES

CRITICAL:

* parser fundamentally cannot implement canonical grammar
* AST corruption across core constructs
* parser hangs/crashes systematically
* major stage contract violation

HIGH:

* major grammar alternative missing
* valid programs systematically rejected
* invalid programs systematically accepted
* severe AST corruption
* broken precedence/associativity
* source information lost

MEDIUM:

* isolated grammar bug
* significant recovery failure
* important AST/span issue
* substantial missing test coverage

LOW:

* minor diagnostic quality
* isolated span edge case
* minor test gap
* non-critical consistency issue

Do not inflate severity.

# 52. CRITICAL DISTINCTION

The audit must distinguish these four situations:

### A. Implementation is wrong

Example:

```text
Spec says X.
Parser accepts Y.
```

→ IMPLEMENTATION BUG.

### B. Implementation may be correct but tests are weak

Example:

```text
Parser implements X.
No test distinguishes X from broken behavior Y.
```

→ TEST GAP.

### C. Specification does not define the behavior

Example:

```text
Both X and Y are compatible with the written specification.
```

→ SPEC GAP / OPEN.

### D. Stage 2 is being asked to perform a later-stage responsibility

Example:

```text
Parser rejects undeclared variable.
```

if declaration checking belongs to semantic analysis.

→ Do NOT call it a Stage 2 failure merely because the behavior is unexpected.

---

# 53. STOP CONDITIONS

Do not stop merely because:

* all current tests pass
* parser code looks clean
* grammar is small
* no obvious bug appears
* design document says "complete"

Continue until all of the following have been attempted:

[ ] complete canonical specification read
[ ] complete Stage 2 design read
[ ] complete parser read
[ ] complete AST read
[ ] complete diagnostics read
[ ] complete Stage 2 test read
[ ] grammar inventory
[ ] claim-by-claim audit
[ ] production-by-production audit
[ ] precedence audit
[ ] AST audit
[ ] span audit
[ ] token-consumption audit
[ ] error audit
[ ] recovery audit
[ ] valid corpus
[ ] invalid corpus
[ ] adversarial cases
[ ] mutation survivability
[ ] Stage 1 contract audit
[ ] downstream information audit
[ ] repository cleanliness verification

Only then produce the final verdict.

---

# 54. MOST IMPORTANT RULE

Do not optimize for a PASS verdict.

Optimize for discovering the truth.

If Stage 2 is correct, prove why.

If Stage 2 is broken, demonstrate exactly where and how.

If the tests are insufficient, prove that.

If the specification is incomplete, identify the exact missing rule.

If the design is wrong, identify the contradiction.

If something cannot be established from available evidence, mark it UNPROVEN.

The purpose of this audit is to establish the strongest defensible evidence about the actual state of Stage 2 — not to provide reassurance.
